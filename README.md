# Diobot

Telegram 群管理工具，TypeScript + grammY + Deno
2。可编译为包含运行时和验证页面的独立二进制，目标机器无需安装 Deno / Node.js。

## 版本与归档

`archive/go-legacy` 保存原 Go 源码，`main` 是 TS 版。原目录没有 Git
仓库，因此归档是新建的源码快照。旧二进制 `diobotnew` 和含部署密钥的本机
`diobot.service` 保留且不提交；正式 `diobot.service` 已切换到
`bin/diobot`，正式数据库为 `var/diobot.sqlite`。原 Go 程序保留，原服务配置备份在
Git 忽略的 `data/deploy/diobot-go.service.backup`。

## 群配置

在群中通过 bot 命令菜单使用 `/settings` 取得 Web
设置和本群日志入口；`/inline_settings`
启动原按钮设置，供网页不可用时回退。命令按 `all_chat_administrators`
范围注册为原生 `is_ephemeral` 命令；bot 用 `sendRichMessage` +
`ephemeral_message_parameters` 返回仅操作者可见的设置面板，按钮使用 rich message
的原生 buttons 块。点击后用 `editEphemeralMessageText` 更新，没有公开消息回退。

需要支持 ephemeral / rich 消息的 Telegram 客户端及 Bot
API。使用旧客户端手动发送普通文本命令时，bot 无法将已经发出的普通消息变成
ephemeral；应从支持此能力的客户端菜单发送命令。匿名管理员须切换为个人身份，bot
无法从匿名发送身份确认其实际管理员权限。

每次打开和点击面板都会查询本群实时管理员身份；按钮绑定操作者、群和设置版本，过期面板会刷新，不会反复翻转开关。配置立即保存到
SQLite，重启后保留。

群内 `/settings` 的“Web 设置”进入 Telegram Mini App
管理页面，显示通过后台验证的用户 ID、群名及群
ID，可编辑上述开关、审核模式和本群独立处理阈值（50%–100%，未配置时使用全局默认
80%）。开关及处理方式修改后立即自动保存，阈值、规则名称、正则表达式和标志在输入框失焦后提交，输入期间不发送保存请求；新增规则与
AND
条件的正则默认为空，填写有效内容后才能保存。客户端与服务端使用同一校验函数检查规则格式、长度、标志及
JavaScript
正则语法。连续修改串行保存，旧响应不会触发提交仍在编辑的内容。底部固定显示保存状态，失败时弹出醒目错误卡片并保留修改。保存后立即生效且重启保留，其他群不受影响。全局调用额度与留存限制只读，密钥不返回浏览器。

首屏在 HTML 起始位置就呈现加载界面，并通过 Telegram 原生 `web_app_ready`
事件提前显示 WebView；不依赖外部 SDK 到达或设置接口返回。SDK
退到首帧后异步加载，隐藏 WebView 有定时兜底。纯静态 HTML
不含身份或群配置，可在浏览器缓存5分钟，源站支持 ETag 校验（公网经 Cloudflare
改写时可能移除该头）；设置、日志、验证接口仍为 `no-store`，权限校验不缓存。

逐脚本 Resource Timing 会分别回传 SDK、页面动态脚本等外部资源的 URL
来源（删除查询参数与片段）和总加载耗时；跨域有 Timing-Allow-Origin
或同源资源时才附加
DNS、连接、TLS、首字节和下载分段。拿不到分段时标记为“仅总耗时可见”，不伪造为零。内联启动另记
`bootstrap_ready`，本群管理员可在日志页的客户端耗时分类查看。

页面不等待 Telegram 外部 SDK
加载，直接将启动签名送交后台验证；设置请求前端最多等待 12 秒，Telegram
权限查询最多等待 8
秒。网络失败提供中文重试提示；设置接口仅记录请求编号、状态及耗时，不记录签名或凭据。

Web 后台校验 Telegram `initData` 的 HMAC 签名和五分钟有效期；目标群取自签名中的
`settings_群ID` 启动参数，而非信任浏览器提交的群
ID。每次加载和保存实时查询用户及 bot 的群权限，只有目标群管理员且 bot
为管理员时允许管理。直接打开网页或转发入口给普通成员不会获得修改权限。群内按钮与
Web 使用同一设置版本，过期版本返回冲突；入群验证与设置入口分别校验，互不能替代。

可配置项：

| 项目         | 行为                                                                                   |
| ------------ | -------------------------------------------------------------------------------------- |
| 入群人机验证 | 开启后，申请入群私信验证；普通邀请链接入群先禁言后验证。直接拉人不验证。               |
| 近期样本记录 | 默认开启；按期限和数量留存普通成员样本，可在 `/review` 私密复核。                      |
| AI 广告审核  | 关闭 → 仅观察 → 自动删除 → 删消息并禁言 → 删消息并封禁，循环切换；和入群验证独立配置。 |
| 欢迎消息     | 独立开关。                                                                             |
| 被封禁消息   | 独立开关。                                                                             |
| 离开消息     | 独立开关。                                                                             |
| 砍树提示     | 永久封禁成员后，私密提示管理员处理其直接邀请的在群成员。                               |

**没有发言检查**。验证通过后直接完成，不要求新人发消息；群内发送的验证链接消息会在恢复权限后自动删除，临时网络故障会后台重试。升级前未记录消息
ID 的旧验证消息无法自动删除。升级时旧的发言任务自动标记完成。

初次观察到一个群时，`PUBLIC_CHAT_IDS` 和 `MODERATION_MODE`
仅用来初始化默认值。已有群始终以数据库配置为准。无 Turnstile
配置时，初始入群验证关闭；有完整配置时，默认在未列入 `PUBLIC_CHAT_IDS`
的群开启。欢迎、被封禁、离开消息和砍树提示默认开启。

关闭入群验证后，未完成申请交由后台批准，待验证的已入群成员恢复原先保存的群默认权限。该开关不会解封此前已经被封禁的账号。

## 邀请追踪与砍树

bot
根据成员变更事件记录“谁直接拉了谁”，按群隔离，退群或自行重新加入后更新关系。只能记录本版本运行后观察到的事件，不能恢复历史上未记录的邀请。

成员被人类管理员**永久封禁**时，bot 给执行封禁的管理员发送 ephemeral rich
提示。临时封禁不触发，bot 自己执行的批量封禁也不会再次触发。

流程：查看名单 → 确认封禁 →
后台执行。预览时冻结名单，不把后来加入的人混入已经确认的操作。只处理当前仍由该成员直接拉入的成员，不递归处理下一层；跳过群主、管理员、已离群成员和
bot 自己。

管理员也可在群里使用 ephemeral 命令 `/tree 用户ID`
重新打开操作。需要当前具有封禁成员权限；原成员必须仍处于永久封禁状态。任务保存到
SQLite，重启可继续；执行时再次检查权限、群设置、原成员封禁状态和目标成员身份。可通过面板查看进度。按钮操作绑定发起管理员和本群，确认窗口十分钟，重复点击不会重复创建任务。

## 其他功能

- 欢迎、退群、临时/永久封禁通知。
- 六分钟入群验证期限，最多三次失败。失败：尚未入群则拒绝申请，已经入群则永久封禁，需要管理员解除才能再次加入。
- 专属验证链接绑定本人、本群、本次申请；新申请淘汰旧链接。校验 Telegram
  签名和有效期，以及 Turnstile 域名、action、cdata。
- SQLite
  保存申请、群配置、邀请关系、砍树任务、群活动和审核结果；未完成申请重启后继续处理。
- 私聊 `/stats`：仅 `OWNER_IDS` 可用，查看新版已经观察到的群、最近活动和 bot
  状态；不能列出 Telegram 上历史全部群。
- 同群的消息和后台任务按顺序处理，不同群可并发。
- `GET /healthz` 仅检查 HTTP 进程存活，不代表 Telegram / Cloudflare 正常。

## 开发和配置

需要 Deno 2.2+，本项目在 Deno 2.9.3 验证。

```sh
cp .env.example .env
chmod 600 .env
# 编辑 .env，填入独立测试 bot token
deno task dev
```

Turnstile 配置可以全部省略，仅运行群设置 / AI
审核；要开启入群验证须提供三项完整配置，正式环境禁止使用自动放行的测试 key。

`TELEGRAM_ENV=test` 使用 Telegram 测试环境自己的 BotFather token。HTTP 默认绑定
`127.0.0.1:8532`，公网由反向代理提供 HTTPS。验证页在 BotFather 配置为 Main Mini
App，URL 指向 `/`。`VERIFY_HOSTNAME` 填网页域名，不含协议或端口。

bot 须为群管理员，具备审批邀请、限制/封禁成员和删除消息权限。应用配置不会授予
bot Telegram 管理员权限。

## AI 审核

配置 `CF_ACCOUNT_ID` 和
`CF_API_TOKEN`，在群面板开启“仅观察”，评估实际消息后再切换自动删除。审核与入群验证独立，适用于任何开启此功能的群。

默认使用 `@cf/cloudflare/clef-flash` 的原生 state/questions
决策接口。审核新消息和编辑消息的文本及媒体说明，并结合发送者显示名、用户名、可见
bio、头像缩略图中的广告文字、二维码和推广线索。资料缓存两分钟；显示名、用户名跟随消息实时更新。头像最大
128 KiB，使用 Clef
多模态图片输入；通用文本模型完全省略头像字段、摘要和图片，仅直接传图时提供头像线索。消息媒体本身不做识图或语音识别。

提示词特别关注 `t.me/`、`t.me/+`、`t.me/joinchat/`
等加群链接（包含文字超链接目标）、“进群/加群/点击加入”等文字，以及 👉👇🔗➕
等指向链接或账号的引流符号。以邀请链接或入群引导为主的消息可作为主动引流证据；正常技术链接、举报引用和单个符号仍按发言意图判断。

提示词也覆盖孤立姓名、姓名列表和姓名式引流，但要求结合赌博、跑分、洗钱招募或联系方式等推广证据。真实姓名、普通人像、自我介绍和正常称呼本身不足以判广告；举报、合法讨论和求助仍按正常处理。不可见资料明确标为缺失，不推断身份或敏感特征。

上传和记录之前实时查询发送者权限，排除人类及 bot 管理员、bot
自己、`OWNER_IDS`、匿名/频道身份、关联频道自动转发及手动转发；转发管理员消息同样排除，来源或权限无法确认时跳过。资料读取后再次检查；成员升为管理员时清理其本群近期样本。不会向模型上传最近聊天历史。

管理员回复普通成员消息，使用 **`/check`** 原生 ephemeral
命令，可私密查看分类、各项概率、处理阈值、资料可见状态和模型理由。本次仅检查，不删除；群自动审核关闭时也可手动检查。仍遵循管理员及关联频道排除规则，共用每日调用额度和有效缓存。未回复消息时显示使用方法。

模型只输出正常、垃圾广告（含诈骗和非法资金推广）两个选项的概率；不设置“不确定”竞争类别。低概率消息由程序按本群阈值保留，历史三/四分类记录仍兼容读取。数值范围、概率总和和分类一致性均须通过校验；合并后的分类达到
`AI_CONFIDENCE_THRESHOLD`（默认 0.80）才标为 high。模型概率不代表实际正确率。
自动删除模式删除 high
的垃圾广告；“删消息并禁言”模式另将发送者持续禁言，成员留在群内，由管理员解除，不踢出或封禁。禁言需要
bot 有限制成员权限。“删消息并封禁”模式永久封禁发送者，需 bot
有限制成员和删消息权限。
网络故障、输出异常或配额耗尽时保留消息；删除成功但禁言或封禁失败会单独记录。旧四分类响应兼容合并广告与诈骗概率；旧人工诈骗标注在面板统一显示为垃圾广告。

`CF_MODEL` 也支持 `@cf/cloudflare/clef`。通用文本模型适配保留，Qwen
使用关闭思考的 raw 模板和 JSON 输出模式，不把内部 reasoning
当成最终结论。更换模型、策略或阈值后，旧缓存失效。

`AI_DAILY_LIMIT` 是本数据库每天 UTC 的调用次数限制，不等于 Cloudflare 免费
Neurons
额度，失败调用也计数。相同消息复用匹配当前模型和策略的结果。文字和可见资料、Clef
头像发送到 Cloudflare。缓存只保存输入摘要和分类结果，保留 24
小时；缓存包含资料摘要，更换资料、模型、策略或阈值后不复用旧判断。

近期样本从收到的新消息开始采集，不回补历史。在本地 SQLite
保存文字/媒体说明、资料快照、头像缩略图、模型结果、处理动作及人工标签。默认保留
7 天、每群最多 1000 条、全局最多 10000 条，头像总量最多 32
MiB；过期和超限自动清理，停止采集后旧记录仍按期限清理。`REVIEW_RETENTION_DAYS=0`
可全局禁用，群面板的“近期样本记录”可单独关闭；AI 关闭时仍可留样。

管理员通过 **`/review`** ephemeral rich 面板查看最近 5
条，标为正常/误判、垃圾广告（含诈骗）或不确定，并私密查看当时头像。标注留在本地，供调整提示词，不会自动训练或自动上传历史。

## 自定义规则与日志

Web
中可编辑按顺序匹配的黑白名单正则，支持上移、下移、启停和分组。每条规则/组共用放行或封禁动作，组内1至8个条件按
AND 匹配；首个命中的组立即生效，不再执行后续组或调用 AI。规则独立于 AI
开关；未命中时按本群 AI 设置处理。条件可选择用户名（不含 @）、bio
或消息内容，不可见的 bio 不参与匹配。管理员及关联频道保护在规则前执行。`/check`
优先返回该版本消息已记录的正则匹配规则和实际处理结果，不重新读取资料或调用
AI；没有匹配记录时先检查当前规则，命中后直接返回，不读取头像。检查不会实际处罚。

最多32条规则/组，每个表达式最多256字，支持 i/m/s/u 标志。匹配在独立 worker
中限时执行；超时或失败记入日志并按 AI
设置继续。新建规则默认停用且使用不匹配表达式 `(?!)`。

消息内容统一提取正文、媒体
caption、投票题目/描述/选项、清单标题/任务及新增任务、文档/音频/视频文件名、名片、地点标题、游戏与发票文字、富消息文字和隐藏链接。正则只匹配当前消息；AI
另行接收回复、引用和跨频道来源，明确标为其他作者的参考内容，不把举报者引用的广告归给举报者。不把其他用户新增的投票选项归给原作者。图片像素、文件内容和语音仍不做
OCR/转写。

本群 AI
政策将普通成员发送联系人名片视为强广告、引流信号，不默认解释为正常交换联系人。名片电话、vCard、用户
ID、用户名、联系链接，以及正文、bio 和回复中的可联系对象会随上下文提交给已配置的
Cloudflare AI；不额外查询联系人或抓取链接。“来发财”等招揽短句结合名片、bot
或跨频道入口时加强识别；处理仍遵循本群阈值和模式。Telegram
未提供的外部原文标为缺失，不编造内容。

头像上传为每群独立开关，仅出现在 Web
页面，默认保持开启。关闭后新消息不再下载、留存或上传头像，历史样本按原期限保留；用户名、显示名及
bio 不受影响。开启时仅直接传图模型接收像素。

`/settings` 的“本群日志”打开独立 Web
日志页，实时检查本群管理员权限，展示最近100条本群处理/设置操作、审核样本和客户端耗时，支持类型筛选与刷新。日志凭据不能修改群设置。处理/设置日志保留7天、最多10000条；审核样本按原限制保留。

客户端自动回传页面/SDK就绪、导航
DNS/TLS/首字节、设置加载与保存耗时、HTTP状态、失败类型及请求编号。后台将请求编号与服务端耗时关联；不回传启动签名、完整
URL、消息内容或原始异常文本。离线最多暂存40条，后续连接成功时补传，可在“加载耗时与诊断”手动回传。回传日志验签、按事件ID去重、限制频率，数据库最多10000条，3天后在下一次回传或查看时清理。日志页同时回传读取耗时。

原始消息日志从本版本起在资料读取和AI调用前留存符合采集条件的完整 Telegram
Message 和 Update JSON，包含 Telegram
当次提供的回复、跨频道引用、entities、名片、按钮、媒体 file_id
及未知扩展字段。重复投递按完整消息指纹去重，编辑保留新版本；不截断原始
JSON，分析结果不会覆盖原始内容。默认保留7天、最多10000个版本、总量256MiB，超过限制删除整条旧版本；全部审核/采集功能关闭时不采集。管理员及受保护身份仍排除，升为管理员后清理其原始样本。

Web“本群日志”可筛选“原始消息”，查看或下载完整
JSON；导出每次实时校验本群管理员权限且响应不缓存，不能读取其他群。附件保存
Telegram 提供的元数据和
file_id，不自动下载全部媒体二进制。管理员可点击“AI重新分析（不处罚）”，使用留存原文和当时的资料上下文按当前政策重新调用
AI，绕过旧判断缓存但共享每日额度；不执行封禁、禁言或删除，原判断保留，新结果另记日志。Telegram
当次未提供的跨频道原文、或以前未留存的字段不能补回。

## 图片与 Sticker 黑名单

各群独立维护图片、Sticker
名单，两类分别启用并配置动作：观察、删除、删消息并禁言、删消息并永久封禁。默认均关闭，启用时默认删除消息；与
AI
开关独立。管理员、OWNER_IDS、匿名及关联频道保护继续生效；媒体黑名单优先于正则白名单，命中后不调用
AI。

管理员回复图片、图片文件或 Sticker，使用原生 ephemeral `/blacklist`，选择加入
unique ID、PDQ Hash，Sticker
有所属组时还可加入整个组。添加不会处理被回复消息或扫描历史，只影响后续消息和编辑。按钮绑定操作者、本群、媒体，六分钟有效；重复添加不产生重复条目。图片
ID 会保存 Telegram 提供的各尺寸 unique ID 别名。组名匹配覆盖该组之后新增的
Sticker。

在 `/settings` 的图片、Sticker 黑名单卡片中启用功能、选择动作、调整 PDQ
参数，以及加载名单、修改备注、删除条目。数值和备注在输入框失焦后保存；客户端与服务端使用相同的策略校验。设置和名单共享群
revision，旧页面提交会提示重新加载。每群每类最多1000条，SQLite 持久保存。

图片支持 Telegram photo 及 JPEG、PNG、WebP 图片文件，不包含普通视频和
GIF。静态图片与 WebM 使用嵌入的精简媒体解码 WASM，WebM
只取第一帧并保留透明通道；TGS 使用嵌入的 rlottie WASM
渲染第一帧，透明区域统一白底，再由 PDQ WASM 计算256位 hash 和0–100
Quality。所有解码、渲染和 hash 均在有截止时间的 WASM Worker
中执行，不下载运行时代码，也不使用 Telegram 缩略图代替原媒体。

PDQ 最大汉明距离默认31（可设0–256），最低 Quality
默认50（可设0–100）。当前媒体和名单条目的 Quality
都必须达标，距离不大于阈值才算匹配。低 Quality
条目可保存，页面和添加回执会提示其在当前门槛下不参与匹配；ID 和组名匹配不受
Quality 限制。名单按图片和 Sticker 分开匹配。

下载限制20 MiB，解码上限1600万像素，TGS解压上限4
MiB；单项处理限时10秒，全局最多同时处理两项。下载、解码或 hash
失败保留消息、记日志并继续原正则和 AI 流程。计算缓存按 unique ID
和处理版本复用，最多10000项；媒体解码在内存中完成，不创建临时媒体文件。`/check`
显示媒体黑名单的实际历史结果或当前匹配依据，包括距离及双方 Quality，但不会处罚。

`GET /api/media-blacklist` 获取本群名单与策略；`POST` 添加条目，或使用
`operation: "note"` 修改备注；`DELETE` 按条目 ID 删除。写请求均携带当前群
revision；添加 PDQ 需64位十六进制 hash 和 Quality。认证和权限与 `/api/settings`
一致，不接受未签名的目标群。旧客户端不传 `media` 时保留已有媒体设置。

构建使用固定上游版本，详情见 [native/README.md](native/README.md)。运行时只需要
bot 二进制：图片/WebM 解码、TGS 渲染和 PDQ 的 WASM 均已嵌入，不需要安装
FFmpeg、FFprobe、Lottie 或其他外部程序，也不需要
`--allow-run`。媒体处理完全在内存中完成，不落地临时媒体文件。发布前执行
`./dist/diobot --check-media`，离线验证嵌入的 PDQ、rlottie、Worker
和解码链，不连接
Telegram、不修改运行数据库。部署可保留默认关闭，再由各群管理员分别启用。

```sh
deno task check

deno task compile
./dist/diobot --version

```

`dist/diobot` 包含 Deno 运行时和验证页面。当前 Linux x64 产物约 107
MB。密钥通过进程环境提供，不会嵌入产物。开发启动任务读取 `.env`，独立二进制由

## 本地 Telegram Bot API

使用本机实例时设置 `API_ROOT=http://127.0.0.1:8081`。若实例开启
`--local`，再配置 `LOCAL_BOT_API_FILE_ROOT`
为该实例的数据目录；服务账号需要只读访问权限。头像只读取该目录内解析后的实际文件，拒绝目录外路径及越界符号链接，仍执行大小和格式校验。相对路径继续通过配置的
API 下载。

从官方云端迁移时先停止 bot，调用官方 `logOut`，然后切换 API
并启动；迁移后十分钟内不能登录回官方云端。本地 API 与 Cloudflare AI 的配置独立。

## GitHub 自动构建与发布

提交到 `main` 或提出 PR 时运行检查、测试及 Linux x86_64 构建，成功后可下载
Actions artifact。推送 `v*` 标签（例如 `v1.0.0`）自动创建
Release，包含压缩包、SHA-256
和包内源码提交记录。仓库运行配置、数据库、媒体和凭据不会进入发布包。

也可在 Actions → Build and Release → Run workflow 手动运行；`release_tag`
留空只构建，填入已存在的版本标签才发布该标签对应代码。已有 Release
不自动覆盖，发布需要修改版本标签。无需额外配置个人令牌，发布 job
使用仓库自动提供的 GITHUB_TOKEN。

构建产物面向 Debian 13/Linux x86_64；其他架构和系统版本不作保证。
